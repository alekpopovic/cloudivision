# cloudivision v0.2 implementation plan

## Purpose

This plan turns the [v0.2 roadmap](v0.2.md) and
[prioritized backlog](backlog.md) into an executable release sequence. v0.2 is a
focused reliability increment: prove one production-shaped path from an
authenticated GitHub event to an immutable registry digest and an observable
GitOps deployment.

Work is delivered as complete vertical slices. An item is complete only when
its CRD/API contract, runtime behavior, tests, documentation, and user-facing
diagnostics agree.

## Goals

1. **Reliable image build:** rootless BuildKit validates inputs, reports bounded
   failures, and remains optional for non-image pipelines.
2. **Registry push with digest capture:** private-registry credentials remain
   secret and a successful BuildRun records the pushed digest.
3. **Production-ready GitHub webhooks:** signed push and pull-request events are
   filtered, replay-resistant, and idempotent across API restarts.
4. **GitOps release MVP:** a Release updates an allowed Helm values path with an
   immutable image and reports Argo CD convergence or a bounded failure.
5. **Better Angular debugging UX:** source, build, push, policy, GitOps, and
   deployment stages are visible without reading controller logs.
6. **Security baseline enforcement:** least-privilege RBAC, safe Pod defaults,
   redaction, OIDC authorization, and documented egress are release gates.

## Delivery rules

- Desired and runtime state remain in CRD spec/status. PostgreSQL may store
  webhook idempotency and audit records, not BuildRun or Release truth.
- Add fields compatibly to `v1alpha1`; regenerate CRDs and Helm CRDs together.
- Provider behavior stays behind small builder, Git, GitOps, auth, audit, and
  provider interfaces.
- Retries are bounded and idempotent, with external-operation checkpoints.
- Secret values never enter logs, status, events, API errors, metrics, or audit
  attributes.
- Named registry, PostgreSQL, Git, OIDC, and Argo CD acceptance tests must run
  against those real dependencies; unit substitutes are not sufficient.

## Epic 1 — Image build and registry

### Problem and user value

v0.1 did not prove rootless BuildKit against an authenticated registry. Tags
alone are mutable and incomplete push status cannot identify the artifact to
deploy. This epic lets a team configure one scoped credential and produce an
auditable immutable digest.

### Technical approach

- Harden BuildKit availability, context and Dockerfile validation, command
  construction, build args, targets, platforms, labels, cache, push, timeouts,
  metadata digest parsing, and error classification.
- Implement a generic Docker Registry provider, with named GHCR, GitLab Registry,
  and Harbor adapters. ECR, GCR/Artifact Registry, and ACR remain explicit
  skeletons unless needed by the release fixture.
- Project only the configured Kubernetes Secret into the runner. Support
  username/password, token, and `.dockerconfigjson` without copying secrets into
  CRDs.
- Generate deterministic registry-safe tags and store repository, tag, and digest
  separately. Release inputs prefer `repository@sha256:...`.
- Retry only transient registry operations with bounded exponential backoff.

### Work items

1. **IMG-01 — BuildKit adapter hardening:** validation, command generation,
   optional settings, metadata digest parsing, and clear failure reasons.
2. **IMG-02 — Registry provider and credentials:** provider contract, secret
   parsing/projection, health reporting, and redaction.
3. **IMG-03 — Tag and immutability policy:** templates, sanitization, `latest`
   policy, digest status, and production digest enforcement.
4. **IMG-04 — Registry integration fixture:** authenticated rootless push,
   transient failure recovery, and remote digest verification.

### Required CRD and API changes

- Extend `PipelineTemplate.spec.build` with optional `buildArgs`, `target`,
  `platforms`, `labels`, and cache configuration.
- Add project or repository registry provider, `imagePrefix`, and namespaced
  `credentialSecretRef` configuration.
- Add tag-template, `allowLatest`, and production `requireDigest` policy at the
  narrowest existing configuration boundary.
- Ensure `BuildRun.status.image` exposes `repository`, `tag`, and `digest`, plus
  stable build, push, and digest conditions.
- Return stable errors for bad input, unavailable BuildKit, credentials, push,
  digest resolution, and policy denial.

### Test plan and acceptance criteria

- Unit-test command generation, optional settings, missing context/Dockerfile/
  `buildctl`, push disabled, malformed metadata, credential parsing, redaction,
  unsupported providers, and tag sanitization.
- Reconcile-test that a runner receives only the named Secret and has no broad
  Secret permission.
- Integration-test an authenticated push, remote digest lookup, and one transient
  retry. Status must contain a valid `sha256` digest and Release must use it.
- `go test ./...` and `go vet ./...` pass; non-build pipelines work without
  BuildKit; every failure has a stable reason; no credential is exposed; no
  Docker socket, privileged mode, or cluster-wide Secret access is introduced.

### Risks and dependencies

Rootless snapshotters vary, so availability must fail early with documented
supported modes. Multi-platform output may be an index digest; tests must pin the
recorded meaning. Retries use the same content identity so an existing digest is
success. `IMG-01` precedes `IMG-02/03`; all precede `IMG-04` and digest-based
GitOps work.

## Epic 2 — Webhooks

### Problem and user value

Signature checks exist, but payload bounds, event normalization, branch policy,
durable delivery claims, and restart behavior are not production-proven. This
epic ensures one valid GitHub event creates at most one correctly attributed
BuildRun and rejected events create none.

### Technical approach

- Verify `X-Hub-Signature-256` with constant-time HMAC comparison before parsing
  and enforce a configurable body-size limit.
- Normalize push and pull-request payloads; `ping` returns success without a
  BuildRun. Apply event and branch include/exclude filters before creation.
- Atomically persist `X-GitHub-Delivery` with TTL through the idempotency backend;
  use PostgreSQL for restart safety and memory only for development.
- Reject a replay only where trustworthy event data establishes staleness; do not
  invent a timestamp GitHub does not sign.
- Emit bounded accepted, rejected, duplicate, and BuildRun-created audit events
  without storing or logging full payloads.

### Work items

1. **WH-01 — HTTP security boundary:** signature, body limit, stable responses,
   safe logging, ping, and parser error mapping.
2. **WH-02 — Event filtering:** push/PR metadata, branch and event filters, and
   explicit ignored responses.
3. **WH-03 — Durable delivery claims:** atomic interface, PostgreSQL storage and
   migration, TTL cleanup, and restart test.
4. **WH-04 — Audit and conformance:** required events, bounded metrics, fixtures,
   redelivery tests, and exact GitHub setup documentation.

### Required CRD and API changes

- Extend `Repository.spec.webhook` with push/PR enablement and branch filters if
  absent.
- Store normalized trigger type, ref/branch, SHA, pull-request number, and
  delivery ID in BuildRun metadata, never the payload.
- Stabilize JSON results for accepted, ignored, duplicate, malformed,
  unauthorized, and oversized requests.
- Preserve `POST /api/v1/webhooks/github/{repositoryName}` and existing
  namespace/auth scope.

### Test plan and acceptance criteria

- Unit/request-test valid, missing, malformed and invalid signatures; push, PR,
  ping, malformed JSON, ignored branch/action, missing delivery ID, and oversized
  body.
- Invalid, excluded, malformed, or oversized requests must never invoke BuildRun
  creation.
- Concurrent delivery and post-restart PostgreSQL redelivery must produce exactly
  one BuildRun.
- Valid push and PR fixtures have distinct correct metadata; `ping` succeeds with
  no BuildRun; audit records contain bounded metadata but no payload/secret.
- `go test ./...`, `go vet ./...`, and deployed GitHub conformance pass.

### Risks and dependencies

Fail closed if durable idempotency is configured but unavailable. Return a stable
ignored reason for surprising filters. Size delivery retention from documented
redelivery behavior. `WH-01` precedes the epic; `WH-02` and `WH-03` may run in
parallel; both precede `WH-04`.

## Epic 3 — GitOps release

### Problem and user value

v0.1 did not commit an immutable image to a real writable GitOps repository or
observe real Argo CD health. This epic lets users promote one exact digest and
distinguish commit, synchronization, health, and timeout failures.

### Technical approach

- Harden direct commit and `helm-values` mutation with path allow-listing,
  structure-preserving YAML updates, optimistic conflicts, and persisted commit
  checkpoints.
- Enforce production digest policy and update Git with
  `repository@sha256:...`.
- Add a read-only Argo CD adapter and map sync/health to provider-neutral Release
  conditions with a deployment deadline.
- Keep PR promotion supported but secondary; add Flux status only after the Argo
  CD contract is stable.

### Work items

1. **GITOPS-01 — Digest-only Helm values update:** allowed file/key, one image
   mutation, and commit checkpoint.
2. **GITOPS-02 — Idempotent conflict handling:** reuse commits and report
   actionable conflicts.
3. **GITOPS-03 — Argo CD health reader:** read-only discovery, state mapping,
   deadline, provider errors, and least-privilege RBAC.
4. **GITOPS-04 — External conformance:** writable repository plus Argo CD success,
   degraded, unavailable, and timeout scenarios.

### Required CRD and API changes

- Stabilize Environment GitOps configuration for an allowed values file/key and
  Argo CD Application reference.
- Record immutable image, commit SHA, provider sync/health, observations,
  deadline, and stable conditions in Release status.
- Add only credential-free links between BuildRun, Git change, provider resource,
  and Release.

### Test plan and acceptance criteria

- Unit-test path validation and values preservation; reconcile-test repeated
  calls, pre/post-checkpoint conflicts, provider outage/degradation, and timeout.
- Assert narrow Git credential projection and read-only Argo CD RBAC.
- A real repository receives exactly one allowed digest update; reconcile reuses
  the commit; Synced/Healthy succeeds; all failure modes have stable conditions.
- Production mutable-only releases are blocked and the runner has no path or
  permission to apply target workloads.

### Risks and dependencies

Limit YAML mutation to configured paths/keys. Treat provider state monotonically
and preserve observations. Resolve uncertain Git outcomes before another commit.
`GITOPS-01` requires Epic 1; `GITOPS-02` builds on it; `GITOPS-04` requires all
three implementation items.

## Epic 4 — Runner reliability

### Problem and user value

The runner coordinates untrusted code, BuildKit, credentials, cancellation,
timeouts, and status. Users need bounded, diagnosable failure and safe transient
recovery without making non-image pipelines fragile.

### Technical approach

- Define stable clone, steps, build, push, digest, and supply-chain stage results.
- Propagate cancellation and deadlines to all I/O and classify configuration,
  policy, user, transient infrastructure, and internal failures.
- Assign retry ownership per operation so controller and runner cannot multiply
  work or artifacts.
- Retain non-root, read-only-root where feasible, no privilege escalation,
  resource bounds, and scoped credential volumes.

### Work items

1. **RUN-01 — Stage/error contract:** stable reasons, conditions, deadlines, and
   redaction boundaries.
2. **RUN-02 — Cancellation and bounded retries:** context propagation and tested
   Git/registry retry policy.
3. **RUN-03 — Workspace lifecycle:** safe paths, clean context and cleanup, with
   optional isolated cache only.
4. **RUN-04 — Reliability conformance:** timeout, cancellation, pod loss,
   transient push, status conflict, and optional BuildKit.

### Required CRD and API changes

- Prefer conditions and existing status; add only stable stage data used by API
  and UI.
- Bound any configurable attempts/timeouts in CRD schema and controller policy.
- Expose cancel/retry actions only after idempotency and authorization are fixed.

### Test plan and acceptance criteria

- Unit-test retry classes, redaction, safe paths, and cancellation; reconcile-test
  conflicts, Job loss, repeated terminal observation, and cleanup.
- All I/O honors cancellation/timeouts; failures identify stage/reason without
  leaking environment or secrets; retry cannot create a second logical artifact.
- Job loss, cancellation, and timeout become terminal; non-build pipelines need
  no BuildKit/registry Secret; rendered jobs remain least-privilege and bounded.

### Risks and dependencies

Multiple retry layers can multiply work, so attempt ownership is tested. Typed
errors separate sanitized public messages from wrapped causes. Persist bounded
evidence before cleanup. `RUN-01` precedes runner-facing Epics 1 and 5; `RUN-02`
uses the Git/registry error taxonomy; `RUN-04` closes after Epics 1 and 2.

## Epic 5 — UI/UX

### Problem and user value

Existing pages expose resources but not the complete authenticated source-to-
deployment path. A user must be able to validate setup, run a build, copy its
digest, follow the Release, and diagnose stage-specific failure in Angular.

### Technical approach

- Extend onboarding with non-destructive webhook, repository, registry, branch
  filter, and provider-health checks.
- Render persisted clone, steps, build, push, policy, Git commit, sync, and
  deployment stages; show unknown rather than inferred success.
- Display repository, tag, and digest separately and preserve API error code,
  message, correlation ID, and conditions.
- Bound lists/logs, stop polling at terminal state, manage subscriptions, and
  cover empty, loading, forbidden, degraded, and terminal states.

### Work items

1. **UI-01 — Shared stage model:** map backend conditions without guessing.
2. **UI-02 — BuildRun detail:** tag/digest, stage errors, bounded logs,
   correlation IDs, and safe actions.
3. **UI-03 — Release detail:** BuildRun/Git links, provider state, deadline, and
   deployment failure.
4. **UI-04 — Onboarding readiness:** webhook and registry checks with forbidden
   and degraded handling.

### Required CRD and API changes

No UI-only CRD fields. Consume Epics 1–4 status/error contracts. Add narrow,
authorized, redacted readiness endpoints only when existing provider-health APIs
cannot serve the flow. Require pagination and explicit log limits.

### Test plan and acceptance criteria

- Unit-test stage mapping, digest formatting, error preservation, cleanup, and
  safe-action visibility.
- Browser-test onboarding, bad secret, clone/build/push/policy, Git conflict,
  GitOps timeout, forbidden, empty, loading, and terminal states.
- Users can identify a failed readiness check; BuildRun separates tag/digest and
  stages; Release distinguishes commit/sync/health/timeout; backend error and
  correlation ID survive; no secret reaches DOM/console/telemetry; polling and
  retrieval remain bounded.

### Risks and dependencies

Render only persisted state. Authorize/rate-limit readiness checks so they are
not credential probes. Use backoff and stop terminal polling. `UI-01` waits for
the shared condition contract; `UI-02` needs digest status; `UI-03` needs Release
provider status; `UI-04` needs registry and webhook health.

## Epic 6 — Security

### Problem and user value

Safe defaults exist, but production OIDC, provider egress, credential redaction,
used-verb RBAC, and dependency findings are not proven as one baseline. Operators
need a defensible install and exact minimum permissions.

### Technical approach

- Keep the runner threat model and `make security-check` aligned with every new
  Secret, permission, status field, and Helm value.
- Audit actual Kubernetes calls and keep project access namespace-scoped.
- Test OIDC project authorization and cross-project denial.
- Publish/test default-deny plus DNS, Git, registry, PostgreSQL, Argo CD, and
  telemetry egress examples.
- Inventory Go, npm, image, and workflow findings; fix applicable critical/high
  issues or record an owned, time-bounded exception.

### Work items

1. **SEC-01 — Secret/redaction conformance** across registry, webhook, Git, OIDC,
   API, audit, logs, status, events, and metrics.
2. **SEC-02 — RBAC used-verb review** proving namespace scope and no broad Secret
   or target-workload access.
3. **SEC-03 — OIDC conformance** for valid, forbidden, cross-project, expired,
   and invalid tokens.
4. **SEC-04 — NetworkPolicy baseline** for required and denied egress.
5. **SEC-05 — Dependency triage** with remediation and exception records.

### Required CRD and API changes

Use namespaced Secret references instead of secret-valued CRD fields. Validate
ownership/scope for each reference. Structured denials may name the cause but
must not echo tokens, headers, Docker config, credential-bearing URLs, or payloads.

### Test plan and acceptance criteria

- Scan rendered Helm for privileged/root defaults, Docker socket, hostPath,
  cluster-admin, broad Secret verbs, and global project bindings.
- Exercise marker credentials through all runtime/output paths; none may persist.
- Run live OIDC and CNI-capable NetworkPolicy conformance.
- The supported flow works under reviewed Roles; valid project access succeeds
  and invalid/cross-project access fails; required egress works while unrelated
  egress fails; no unexplained critical/high production finding remains.

### Risks and dependencies

Provider destinations change, so network examples are topology-specific.
Used-verb tests protect RBAC reductions. Findings are classified by shipped
exposure with owner and expiry. `SEC-01` participates in every credential epic;
`SEC-02` follows final API calls; `SEC-03/04` share conformance infrastructure;
`SEC-05` starts early and closes at release.

## Epic 7 — Docs and release

### Problem and user value

The release is incomplete until installation, upgrade, operations, security,
limitations, artifacts, and clean-cluster evidence describe the same supported
path. Operators must be able to reproduce it and assess known risk.

### Technical approach

- Update BuildKit, registry, webhook, GitOps, UI, API/CRD, security, and
  troubleshooting documentation with implementation.
- Test upgrade from published v0.1.0, not a same-version reinstall.
- Run GitHub, authenticated registry, writable GitOps, Argo CD, OIDC, and
  security conformance without a main-path skip.
- Measure 100 BuildRuns and retain the 10-run smoke test.
- Publish checksums, signatures, SBOM/provenance, migrations, dependency
  dispositions, known issues, and release notes.

### Work items

1. **REL-01 — Feature documentation:** rootless build, registry credentials,
   image tagging, webhook setup/security, GitOps, UI, and failure runbooks.
2. **REL-02 — v0.1-to-v0.2 upgrade:** preserve CRs and prove pre/post-upgrade
   reconciliation with rollback guidance.
3. **REL-03 — External conformance:** all required providers and security paths.
4. **REL-04 — Scale record:** terminal counts, p50/p95 API/log latency, and
   resource use for 10 and 100 BuildRuns.
5. **REL-05 — Release gate/package:** evidence, artifacts, notes, and ship/no-ship
   decision.

### Required CRD and API changes

Document every added/defaulted/deprecated field and stable error/condition in
the API reference and OpenAPI. Include behavioral migration notes even while
`v1alpha1` remains the storage version. Do not add hidden release-only state.

### Test plan and acceptance criteria

- Run Go test/vet, Angular unit/browser/build, Helm render, YAML, security, and
  production dependency gates from a clean checkout.
- Upgrade published v0.1.0 with representative CRs and BuildRuns; verify data,
  reconciliation, and documented rollback limits.
- The quickstart reaches authenticated webhook-to-GitOps on a clean cluster;
  core external scenarios have no skip; 100 BuildRuns meet declared budgets.
- Release notes contain API/CRD changes, migration, known issues, dependency
  exceptions, checksums, SBOM/provenance, and signature verification; the final
  review gives an explicit ship/no-ship recommendation.

### Risks and dependencies

Pin external fixtures and retain diagnostics to separate flake from product
failure. Run upgrade smoke continuously, not only at freeze. Test doc links and
examples. `REL-01` is continuous; `REL-02` follows schema stabilization;
`REL-03` needs Epics 1–3 and 6; `REL-04` needs stable runtime; `REL-05` needs all
must-have criteria.

## Dependency order and milestone exits

1. **Contract baseline:** `RUN-01`, `IMG-01`, `WH-01`, and `SEC-01` define stage,
   error, credential, and webhook boundaries.
2. **Trusted input and artifact:** `IMG-02/03` and `WH-02/03` produce
   authenticated, filtered, idempotent inputs and immutable output.
3. **Milestone 1:** `IMG-04` and `WH-04` prove that a signed filtered delivery
   creates at most one BuildRun and a remotely verified digest.
4. **GitOps core:** `GITOPS-01/02` consume the digest and `GITOPS-03` observes
   deployment state.
5. **Milestone 2:** `GITOPS-04` proves one digest-only change reaches a terminal
   Release based on real Argo CD health; `UI-01/02/03` can then stabilize.
6. **Production workflow:** `UI-04`, `RUN-02/03/04`, and `SEC-02/03/04/05` close
   onboarding, runtime, and security gaps.
7. **Milestone 3/release:** `REL-02/03/04/05` pass clean-cluster, OIDC, network,
   upgrade, external integration, dependency, and 100-BuildRun gates.

## Explicitly excluded from v0.2

- full enterprise organization/team/membership, SCIM, and delegated-admin model;
- multi-cluster control plane or remote agent mode;
- marketplace or general plugin ecosystem;
- full SLSA implementation or general policy-bundle framework;
- hosted SaaS control plane, billing, or subscription quotas;
- a general workflow language or replacement for Argo CD/Flux;
- privileged Docker-in-Docker or Docker socket builds; and
- `v1beta1` migration before v0.2 upgrade evidence is complete.

Provider skeletons may reserve future interfaces, but they are not supported
v0.2 providers and must not delay the critical path.

## Definition of done

An issue or epic is done only when its acceptance criteria pass; CRDs, generated
manifests, Helm CRDs, OpenAPI, API DTOs, and UI agree; named unit, reconciliation,
security, and integration tests pass; secret and untrusted-code handling matches
the threat model; documentation is updated; and limitations or deferrals appear
in the release notes or backlog.
