# cloudivision v0.2 roadmap

## Product increment

v0.2 will turn the usable v0.1 alpha into a dependable path from an authenticated
GitHub event to an immutable image and an observable GitOps deployment. The work
is deliberately centered on the path users already exercise; it is not a broad
provider or enterprise feature expansion.

See the [v0.2 implementation plan](v0.2-implementation-plan.md) for epics,
work-item sequencing, test plans, and release acceptance criteria.

The [v0.1 final gate](../readiness/v0.1-final-gate.md) proved fresh installation,
credential-free builds, logs, webhook idempotency, same-version upgrades, and a
limited 10-BuildRun load. It did not prove a real image push, a writable GitOps
commit, Argo CD convergence, production auth, external supply-chain tools, or a
cross-version upgrade. Those gaps define v0.2.

## User outcomes

By the end of v0.2, a small platform team should be able to:

1. connect a private GitHub repository and registry without placing credentials
   in manifests or logs;
2. turn an authenticated push into one immutable image digest, despite transient
   Git or registry failures;
3. promote that digest through a reviewed GitOps change and see deployment
   progress or a bounded failure in the UI;
4. diagnose source, build, push, policy, and deployment failures without reading
   controller logs; and
5. install a documented production baseline whose RBAC and network behavior are
   continuously checked.

## Scope and sequencing

### Milestone 1 — trusted source to immutable artifact

Exit condition: signed GitHub push events create at most one BuildRun, branch
filters are enforced, and the Job executor pushes an image whose registry digest
is recorded in BuildRun status.

#### 1. Image build and registry reliability

- **Problem:** v0.1 can exercise source and pipeline steps, but its final gate did
  not prove the rootless BuildKit/private-registry path. Tags alone are mutable,
  and transient pushes can leave ambiguous BuildRun results.
- **Proposed solution:** harden the rootless BuildKit adapter behind the existing
  builder interface; project registry credentials through named Secret keys;
  classify retryable push errors; retry with a bounded backoff; resolve and store
  the pushed manifest digest; and make downstream Release inputs use the digest.
- **Acceptance criteria:** an integration test pushes to a disposable authenticated
  registry; a transient push failure recovers without a second BuildRun or image;
  status records a valid `sha256` digest; Release manifests reference
  `repository@digest`; credentials never appear in logs/status; timeouts and
  resource limits remain enforced.
- **Risks:** registry APIs and rootless snapshotters differ; retries may duplicate
  uploads; multi-architecture indexes complicate digest meaning.
- **Dependencies:** BuildKit adapter, Kubernetes Secret projection, registry test
  fixture, BuildRun image status, policy and supply-chain hooks.

#### 2. GitHub webhook production readiness

- **Problem:** v0.1 verifies signatures and idempotency in conformance, but the
  complete production behavior for branch filters, push versus pull-request
  events, durable replay windows, and restart-safe delivery state is not proven.
- **Proposed solution:** normalize push and pull-request events into explicit
  trigger types; evaluate repository branch/event filters before BuildRun
  creation; persist delivery IDs and expiry in the configured idempotency store;
  reject stale timestamps and invalid signatures before parsing payload content;
  expose bounded rejection reasons and metrics.
- **Acceptance criteria:** valid push and PR fixtures produce the expected distinct
  trigger metadata; excluded branches create no BuildRun; duplicate and replayed
  deliveries remain no-ops across API restarts; invalid signatures create no
  Kubernetes resources; secrets and payload credentials are redacted; GitHub
  conformance passes against the deployed API.
- **Risks:** GitHub redelivery semantics can outlive a local cache; overly strict
  replay windows may reject delayed legitimate delivery; filter changes can
  surprise users.
- **Dependencies:** webhook verifier/parser, PostgreSQL idempotency backend,
  Repository trigger schema, audit events, API metrics.

### Milestone 2 — immutable artifact to observable deployment

Exit condition: a successful digest-based BuildRun can update a real writable
GitOps repository, and a Release reaches a terminal state based on Argo CD health
or a documented timeout.

#### 3. GitOps Release MVP

- **Problem:** the v0.1 state machine and commit adapters have unit coverage, but
  the final gate skipped the external commit assertion and did not observe a real
  Argo CD application. Operators cannot yet rely on end-to-end deployment state.
- **Proposed solution:** productionize direct-commit mode and the `helm-values`
  strategy using digest-only image updates; retain idempotent commit checkpoints;
  add a read-only Argo CD sync/health adapter; map provider state into explicit
  Release conditions; enforce a configurable deployment deadline with actionable
  diagnostics.
- **Acceptance criteria:** an integration environment updates one allowed file in
  a writable GitOps repository; retries reuse the recorded commit; the committed
  value is an immutable digest; Synced/Healthy produces `Succeeded`; degraded or
  expired convergence produces a stable failed/timed-out condition; no CI runner
  applies workloads directly to the target namespace.
- **Risks:** Git conflicts and eventual consistency can create misleading state;
  Helm values layouts vary; provider outages must not cause duplicate commits.
- **Dependencies:** Git credentials, Git provider adapter, Release state machine,
  Environment GitOps config, Argo CD read permission, audit storage.

#### 4. Angular CI/CD debugging workflow

- **Problem:** v0.1 has debugging, onboarding, Release, and provider views, but the
  unproven registry and deployment stages do not yet expose a cohesive guided
  path or stage-specific recovery advice.
- **Proposed solution:** extend the existing Repository wizard with webhook and
  registry readiness checks; show clone/build/push/policy/GitOps/deployment stages
  on BuildRun and Release detail pages; link immutable digests and provider
  health; preserve server error codes, correlation IDs, and bounded logs; offer
  safe retry actions only where the API guarantees idempotency.
- **Acceptance criteria:** a user can onboard a repository, identify an invalid
  webhook secret or registry credential, trigger a build, copy the digest, follow
  the linked Release, and distinguish GitOps timeout from build failure; empty,
  loading, forbidden, degraded, and terminal states have browser tests; no UI
  view requires unbounded BuildRun or log retrieval.
- **Risks:** UI stages may imply guarantees the backend does not provide; polling
  can load the API; displaying provider data can leak sensitive configuration.
- **Dependencies:** structured backend errors/conditions, provider health API,
  pagination, log endpoint, digest and Release status fields.

### Milestone 3 — production baseline and release proof

Exit condition: v0.2 passes a clean-cluster gate with authenticated webhook,
private registry, writable GitOps repository, Argo CD health, security checks,
cross-version upgrade, and documented exceptions only.

#### 5. Security baseline closure

- **Problem:** v0.1 has safe workload defaults and a documented runner threat
  model, but production OIDC/integration paths were not exercised, GitHub reports
  unresolved dependency alerts, and NetworkPolicy guidance is not yet a tested
  provider-specific baseline.
- **Proposed solution:** keep `make security-check` mandatory; review controller,
  API, and runner verbs against observed calls; add tests that the API project
  ClusterRole has no cluster-wide binding; provide default-deny plus explicit DNS,
  Git, registry, and observability egress examples; run OIDC and secret-redaction
  conformance; inventory Dependabot findings and record time-bounded exceptions.
- **Acceptance criteria:** rendered defaults contain no privileged, Docker socket,
  hostPath, cluster-admin, Secret enumeration, or global API-project binding;
  OIDC authorization tests cover cross-project denial; runner and API can operate
  under reviewed Roles; NetworkPolicy examples pass on kind with a compatible CNI;
  no unexplained critical/high production dependency finding remains.
- **Risks:** egress addresses are provider-specific; reducing RBAC may break rare
  reconciliation paths; advisory counts include development/build tooling and can
  be noisy.
- **Dependencies:** threat model, Helm security scripts, audit events, OIDC test
  issuer, dependency inventory, conformance environment.

## Release gates

v0.2 is complete only when all of these are true:

- Go tests/vet, Angular build/browser tests, production npm audit, Helm render,
  and security checks pass in CI.
- Clean-kind conformance has no skip for GitHub webhook, authenticated registry,
  GitOps commit, or Argo CD convergence.
- Upgrade from the published v0.1.0 chart to the v0.2 candidate preserves custom
  resources and both pre/post-upgrade BuildRuns reconcile.
- A 100-BuildRun scenario completes within recorded resource and latency budgets;
  the limited 10-run scenario remains a per-change smoke test.
- Release notes document CRD/API changes, migration steps, known issues, artifact
  checksums, SBOM/provenance, and signatures.

## Explicit non-goals

- multi-cluster fleet management;
- billing, quotas by subscription, or enterprise licensing;
- a general-purpose workflow language or replacement for Argo CD/Flux;
- privileged Docker-in-Docker or Docker socket builds;
- a large provider marketplace; and
- automatic migration to a stable CRD API before compatibility evidence exists.

See [the prioritized backlog](backlog.md) for work-item ordering and deferred
scope.
