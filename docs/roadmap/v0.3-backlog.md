# v0.3 prioritized backlog

This backlog implements the [v0.3 roadmap](v0.3.md). Priority follows dependency
order and the v0.2 final-gate evidence. A work item is not complete when only its
API shape exists; its denial, failure, upgrade and operational paths must pass.

## Must-have

### M0. External delivery-path qualification

- **Priority:** must-have.
- **Problem:** rootless authenticated BuildKit, writable GitOps mutation, live
  Argo CD convergence and a true cross-version upgrade remain unproven.
- **User value:** establishes trustworthy v0.3 foundations and prevents new
  orchestration from hiding v0.2 delivery gaps.
- **Proposed solution:** build disposable registry/BuildKit/GitHub/Argo CD
  fixtures and run v0.2.0-to-v0.3 conformance in protected CI.
- **Acceptance criteria:** source-to-digest-to-Git-to-Healthy passes without skips;
  retry is idempotent; secrets are redacted; old CRs and status survive upgrade.
- **Risks:** flaky external systems, credential leaks and slow CI.
- **Dependencies:** published v0.2.0 artifacts and isolated test credentials.

### M1. Persistent organization directory and migrations

- **Priority:** must-have.
- **Problem:** the non-development organization lifecycle is not fully durable or
  administrable.
- **User value:** tenant, team and membership state survives API restarts and can
  be backed up and audited.
- **Proposed solution:** complete PostgreSQL migrations/repository methods for
  organizations, teams, memberships and project grants with transactional CRUD.
- **Acceptance criteria:** create/update/delete/restart tests pass; uniqueness and
  referential constraints are explicit; migration rollback and backup restore are
  rehearsed; every mutation emits an actor-linked audit event.
- **Risks:** destructive membership migration and orphaned access grants.
- **Dependencies:** audit PostgreSQL backend, identity subject conventions and M0
  release environment.

### M2. End-to-end tenant authorization enforcement

- **Priority:** must-have.
- **Problem:** adding persistent tenancy without enforcing it consistently across
  CRs, logs, artifacts, reports, plugins and Kubernetes RBAC creates data leaks.
- **User value:** users see and change only resources granted to their organization
  and project role.
- **Proposed solution:** centralize authorization middleware/policies, require
  organization scope on tenant APIs, and reconcile namespace Roles from grants.
- **Acceptance criteria:** a permission matrix covers all public endpoints and
  controller-created access; cross-tenant list/get/mutate/log/artifact/report
  tests return forbidden; deprovisioning revokes access promptly; admin recovery
  is documented and tested.
- **Risks:** API/RBAC drift, accidental lockout and expensive list filtering.
- **Dependencies:** M1, OIDC fixture, Project namespace isolation and audit.

### M3. RunnerPool API and deterministic scheduler

- **Priority:** must-have.
- **Problem:** experimental remote targets cannot express capacity, labels,
  organization ownership or deterministic selection.
- **User value:** platform teams route builds to controlled capacity by trust,
  architecture and workload requirement.
- **Proposed solution:** add a namespaced RunnerPool CRD/status with labels,
  capacity, allowed project selectors and local/remote mode; implement an
  idempotent scheduler behind the executor interface.
- **Acceptance criteria:** compatible selection is deterministic; unauthorized
  pools are invisible; concurrency is never exceeded; queue reasons and wait time
  are observable; existing local Job builds remain the default.
- **Risks:** starvation, label abuse, status contention and incompatible CRD
  choices.
- **Dependencies:** M2, executor interface, project quotas and API conversion
  strategy.

### M4. Leased remote-agent execution

- **Priority:** must-have.
- **Problem:** the remote-agent experiment lacks authenticated registration,
  exclusive work leases and safe stale-agent recovery.
- **User value:** isolated runners execute builds without central cluster
  credentials and with clear cancellation/failure behavior.
- **Proposed solution:** use workload identity or short-lived tokens, monotonic
  lease generations, heartbeats, acknowledgement, bounded log/evidence upload and
  server-driven cancellation.
- **Acceptance criteria:** one BuildRun executes at most once; expired leases are
  recovered without two active executions; offline agents fail or requeue within
  policy; cancellation and timeout are terminal; pool credentials are mutually
  isolated; protocol/skew tests pass.
- **Risks:** split brain, replay, clock skew, partial evidence and token theft.
- **Dependencies:** M3, secure transport/identity, artifact/log stores and audit.

### M5. GitHub PR promotion and Release lineage

- **Priority:** must-have.
- **Problem:** promotion/rollback actions lack complete ancestry and provider PR
  lifecycle in one queryable model.
- **User value:** release managers can trace and safely advance or restore an
  immutable digest across environments.
- **Proposed solution:** persist parent, promoted-from, rollback-of and superseded
  references; create deterministic GitHub branches/PRs; reconcile merge/close;
  expose lineage through API, SDK, UI and audit export.
- **Acceptance criteria:** one digest promotes through three environments; retry
  reuses a PR; stale promotion is rejected; rollback selects a successful
  ancestor; approval and merge actors are recorded; provider failures are
  bounded and recoverable.
- **Risks:** Git history rewrites, branch protection variance and concurrent
  promotion conflicts.
- **Dependencies:** M0, M2, GitHub credentials, Release state machine and Argo CD.

### M6. Durable evidence store and promotion policy

- **Priority:** must-have.
- **Problem:** supply-chain references can point to workspace-local/noop output
  that disappears with the runner Job.
- **User value:** every deployed digest has retrievable SBOM, scan, signature and
  provenance evidence governed by organization policy.
- **Proposed solution:** persist evidence immutably, verify it by digest, authorize
  downloads, add retention, and evaluate signed/SBOM/vulnerability policy before
  M5 promotion.
- **Acceptance criteria:** real tool adapters produce evidence that survives Job
  deletion; digest mismatch is rejected; critical and unsigned policies block;
  exceptions expire and are audited; retention and access-denial tests pass.
- **Risks:** key custody, stale vulnerability databases, sensitive SBOM data and
  artifact cost.
- **Dependencies:** M0 digest, M2 authorization, artifact store, scanner/signer
  secrets and policy engine.

### M7. Supported plugin configuration lifecycle

- **Priority:** must-have.
- **Problem:** plugin metadata/schema/health exist, but invalid configuration can
  still diverge from runtime behavior.
- **User value:** operators diagnose integration readiness before a build or
  release consumes the plugin.
- **Proposed solution:** validate startup configuration against JSON Schema,
  publish compatibility/version rules, standardize secret-safe readiness reasons
  and add configuration/upgrade fixtures for supported v0.3 plugins.
- **Acceptance criteria:** malformed config is rejected; missing secrets are
  reported without values; API/UI distinguish unconfigured/unhealthy/incompatible;
  required Git, registry, build, GitOps, policy and supply-chain plugins pass
  contract tests.
- **Risks:** configuration schema drift and provider-specific abstractions.
- **Dependencies:** plugin registry v1, provider adapters, generated clients and
  M0/M6 integration fixtures.

### M8. Operational qualification and recovery gate

- **Priority:** must-have.
- **Problem:** v0.2 has limited scale and same-code lifecycle evidence without
  measured latency/resources or production backup/restore.
- **User value:** operators have capacity expectations, alerts and rehearsed
  recovery before adopting remote execution and durable tenancy.
- **Proposed solution:** automate dashboards/alerts, 100-BuildRun and large-log
  measurements, PostgreSQL/CR/artifact restore and v0.2.0-to-v0.3 upgrade.
- **Acceptance criteria:** injected controller, runner, provider and queue failures
  alert; 100 runs meet published terminal/p95/resource budgets; 100 MB logs remain
  bounded; restore meets RPO/RTO and preserves grants, audit and evidence; final
  gate stores machine-readable results.
- **Risks:** noisy measurements, expensive environments and incomplete restore
  coverage.
- **Dependencies:** M1–M7, metrics-server/Prometheus and external storage fixtures.

## Nice-to-have

### N1. Organization administration and access-review UI

- **Priority:** nice-to-have.
- **Problem:** v0.2 organization views expose data but do not offer a complete,
  safe delegated-administration workflow.
- **User value:** org admins manage teams/grants and review effective access
  without API scripting.
- **Proposed solution:** reactive forms for membership/project grants, effective
  permission preview, confirmation and audit-history links.
- **Acceptance criteria:** UI tests cover allowed, forbidden, empty, conflict and
  deprovisioning states; privilege escalation is rejected server-side; no identity
  or secret data leaks across organizations.
- **Risks:** UI implying authority and accidental bulk revocation.
- **Dependencies:** M1/M2 stable APIs and audit reports.

### N2. Flux health and promotion parity

- **Priority:** nice-to-have.
- **Problem:** the supported v0.3 live topology focuses on Argo CD while Flux
  users need provider-neutral lineage and health.
- **User value:** Flux users see the same Release conditions without surrendering
  GitOps ownership.
- **Proposed solution:** implement the stabilized read-only health interface for
  Kustomization and HelmRelease and reuse M5 lineage.
- **Acceptance criteria:** Ready, degraded, missing and timeout fixtures map to
  provider-neutral conditions; RBAC is read-only; retries do not change Git twice.
- **Risks:** Flux API/version differences and premature provider parity.
- **Dependencies:** M5 contract, Flux test fixture and read-only credentials.

### N3. Dynamic plugin protocol design, not execution

- **Priority:** nice-to-have.
- **Problem:** third-party extensions need a future isolation boundary, while
  loading code into the API process would expand the v0.3 security scope.
- **User value:** contributors get a reviewable extension direction without an
  unsafe marketplace promise.
- **Proposed solution:** write an ADR/prototype protocol covering identity,
  capability/version negotiation, timeouts, resource limits and failure isolation;
  do not load or distribute third-party binaries in v0.3.
- **Acceptance criteria:** threat model and compatibility ADR are approved; a
  disposable prototype proves failure isolation; production feature remains off.
- **Risks:** designing before real provider needs and accidental support promises.
- **Dependencies:** M7 lessons, remote-agent security model and plugin threat model.

### N4. Extended scale and endurance profile

- **Priority:** nice-to-have.
- **Problem:** M8's 100-run gate does not establish long-duration or multi-pool
  behavior.
- **User value:** larger evaluators gain evidence for sizing and bottleneck
  planning.
- **Proposed solution:** add opt-in 1,000-BuildRun, 50-runner, webhook burst and
  24-hour scenarios with cost caps and machine-readable output.
- **Acceptance criteria:** results include terminal count, queue time, p50/p95 API,
  reconcile rate, pod/storage use and failure classification; tests cannot target
  an unapproved non-disposable context.
- **Risks:** infrastructure cost and non-reproducible shared-runner results.
- **Dependencies:** M3/M4 pools, M8 metrics and a dedicated load environment.

## Deferred backlog

- SCIM and automated identity lifecycle beyond manual/OIDC-backed membership;
- billing, plans, entitlements and usage charging;
- public plugin marketplace, arbitrary binary loading and dynamic installation;
- general multi-cluster failover/fleet management beyond explicit runner pools;
- stable `v1` storage migration and `v1alpha1` removal; and
- a general-purpose DAG or workflow engine.

## Backlog operating rules

- Finish M0 before accepting distributed execution changes.
- M1 and M2 ship together; persistence without enforcement is not releasable.
- M3 and M4 remain experimental until duplicate, expiry, cancellation and
  credential-isolation tests pass.
- M5 cannot promote mutable tags; M6 evidence is keyed by the same digest.
- M8 is release work, not an optional documentation task.
- Nice-to-have work is dropped before any must-have exit condition is weakened.
