# cloudivision v0.3 roadmap

## Product increment

v0.3 will turn the broad v0.2 alpha surface into one operable vertical slice for
an internal platform team: an authorized organization assigns a project to a
bounded runner pool, produces immutable supply-chain evidence, and promotes the
result through an auditable GitOps lineage.

The [v0.2 final gate](../readiness/v0.2-final-gate.md) proved clean installation,
API-backed webhook conformance, a dogfood BuildRun, same-code upgrade lifecycle,
limited scale, security checks and release packaging. It did not prove a private
rootless BuildKit push, an external GitOps commit, a true v0.1-to-v0.2 upgrade,
Job per-step images, production OIDC, or measured scale. Those gaps are entry
criteria for new v0.3 work, not deferred release polish.

The detailed sequence and work-item ownership live in the
[v0.3 backlog](v0.3-backlog.md).

## Scope guardrails

v0.3 deliberately proves one supported topology before broadening providers:

- GitHub source and pull requests;
- one OCI-compatible authenticated registry;
- one reviewed rootless BuildKit deployment pattern;
- Kubernetes Job plus one remote runner-pool path;
- Argo CD for live health, with Flux remaining compatible but optional; and
- trusted in-process plugins only.

Billing, SCIM, a public plugin marketplace, arbitrary downloaded plugin code,
general workflow-language features, automatic multi-region failover and a stable
`v1` CRD API are explicit non-goals.

## Release outcomes

### 1. Close the external v0.2 delivery path

- **Priority:** must-have.
- **Problem:** v0.2 has strong unit coverage, but its final gate did not execute
  rootless BuildKit against an authenticated registry or mutate a writable GitOps
  repository. The upgrade test used the candidate on both sides.
- **User value:** operators can trust that the advertised source-to-digest-to-Git
  path works before adopting new v0.3 control-plane features.
- **Proposed solution:** maintain disposable GitHub, registry, rootless BuildKit
  and Argo CD fixtures; run a published v0.2.0-to-v0.3 upgrade rehearsal; verify
  digest capture, redaction, idempotent commit/PR behavior and deployment health.
- **Acceptance criteria:** a signed event creates one BuildRun; an authenticated
  push records the registry manifest digest; exactly one allowed GitOps change is
  produced; Argo CD reaches Synced/Healthy; pre-upgrade resources survive; no
  external-path conformance assertion is skipped.
- **Risks:** external-service flakiness, registry differences, rootless
  snapshotter constraints and test-credential custody.
- **Dependencies:** v0.2 BuildKit, webhook, registry, GitOps and upgrade harnesses;
  isolated credentials and a disposable test environment.

### 2. Enforce durable organization and project tenancy

- **Priority:** must-have.
- **Problem:** v0.2 exposes organizations, teams, memberships and project access,
  but the development directory is permissive and production persistence and
  authorization coverage are not complete across every API and controller path.
- **User value:** platform administrators can delegate project administration
  without allowing one tenant to observe or mutate another tenant's builds,
  releases, logs, artifacts or credentials.
- **Proposed solution:** persist organizations, teams, memberships and project
  grants in PostgreSQL; require organization context on scoped APIs; centralize
  permission evaluation; reconcile namespace access from explicit grants; audit
  every membership and role change.
- **Acceptance criteria:** CRUD and deprovisioning survive restart; admin,
  org-admin, project-admin, developer, viewer and auditor permissions are tested;
  cross-organization API, log, artifact and Kubernetes access is denied; removing
  membership revokes access without deleting project runtime state; all changes
  have attributable audit events.
- **Risks:** authorization drift between API and Kubernetes RBAC, lockout during
  migration, ambiguous ownership and high-cardinality audit data.
- **Dependencies:** OIDC identity, PostgreSQL migrations/backup, existing authz
  policy and organization directory, Project namespace reconciliation.

### 3. Schedule bounded work through runner pools

- **Priority:** must-have.
- **Problem:** the v0.2 remote runner and cluster-target work is experimental; it
  lacks durable pool registration, label selection, leases, heartbeats and a
  failure boundary suitable for untrusted repositories.
- **User value:** teams can isolate workloads by trust, architecture, region or
  capacity without giving the central controller broad remote-cluster access.
- **Proposed solution:** introduce namespaced RunnerPool desired state with labels,
  concurrency and allowed project selectors; use short-lived work leases and
  scoped agent credentials; make heartbeats, cancellation, timeout and stale-lease
  recovery explicit; keep the local Job executor as the fallback pool.
- **Acceptance criteria:** an authorized BuildRun selects one compatible pool;
  capacity is never exceeded; duplicate delivery cannot execute the same lease
  twice; offline agents cause bounded queued/failed status; cancellation reaches
  the agent; compromise of one pool credential cannot read another pool or
  organization; local Job behavior remains compatible.
- **Risks:** split-brain execution, credential theft, clock skew, queue starvation
  and distributed cancellation races.
- **Dependencies:** durable tenancy, remote-agent executor interface, ClusterTarget
  experiment, workload identity, metrics and audit events.

### 4. Make promotion and rollback a lineage, not isolated actions

- **Priority:** must-have.
- **Problem:** v0.2 supports promotion, rollback and multiple GitOps mutation
  strategies, but it does not yet provide a complete environment lineage across
  pull requests, merges, superseded releases and rollbacks.
- **User value:** a release manager can answer what digest is in each environment,
  where it came from, who approved it and which prior release a rollback restores.
- **Proposed solution:** model immutable parent/promotion/rollback references;
  create deterministic GitHub pull requests with evidence summaries; reconcile
  open, merged and closed PR state; prevent stale promotion; expose lineage in API,
  UI and audit exports; retain direct commit as an explicit lower-governance mode.
- **Acceptance criteria:** dev-to-staging-to-production promotion preserves one
  digest lineage; retry reuses one branch/PR; approvals and merge identity are
  recorded; stale or policy-denied promotion changes no Git data; rollback points
  to a known successful ancestor and creates an auditable GitOps change; no runner
  applies target manifests directly.
- **Risks:** provider/branch-protection differences, force-pushes, concurrent
  promotion races and misleading health during eventual consistency.
- **Dependencies:** external delivery-path proof, GitHub adapter, Environment and
  Release status, organization roles, audit storage and Argo CD reader.

### 5. Persist and enforce supply-chain evidence

- **Priority:** must-have.
- **Problem:** v0.2 can generate SBOM, scan, signature and provenance references,
  but noop defaults and workspace-local files do not provide durable evidence or
  a reliable promotion gate.
- **User value:** security and release teams can verify exactly which source,
  builder, dependencies, vulnerabilities and signature produced a deployed digest.
- **Proposed solution:** persist immutable evidence through the artifact-store
  interface; integrate one supported SBOM/scanner/signer/provenance toolchain;
  verify evidence by digest; evaluate organization/environment policy before
  promotion; provide authorized downloads and retention/audit rules.
- **Acceptance criteria:** evidence survives Job cleanup; every reference is bound
  to the image digest; critical-vulnerability and unsigned-image policies block
  promotion with structured reasons; exceptions require an authorized, expiring,
  audited decision; secret/key material never reaches evidence or logs; retention
  deletion is authorized and auditable.
- **Risks:** scanner database freshness, signing-key custody, artifact cost,
  sensitive SBOM contents and policy false positives.
- **Dependencies:** authenticated digest path, artifact storage, policy engine,
  tenancy/authz, audit retention and external secret management.

### 6. Turn the static plugin catalog into an operator contract

- **Priority:** nice-to-have; becomes must-have only for plugins used by the
  supported v0.3 topology.
- **Problem:** v0.2 registers trusted plugins in process and exposes metadata and
  health, but configuration schemas are descriptive and startup/upgrade behavior
  is not an operator-facing lifecycle.
- **User value:** operators can see which integrations are available, configured,
  compatible and healthy before assigning them to projects or runner pools.
- **Proposed solution:** validate plugin configuration against its published JSON
  Schema; expose safe readiness reasons and version compatibility; document the
  provider adapter contract; add configuration examples and upgrade tests; keep
  code statically compiled and reviewed.
- **Acceptance criteria:** invalid configuration fails startup or readiness with
  a secret-safe actionable reason; API/UI distinguish unavailable from
  unconfigured; every supported provider declares version, capabilities, schema,
  docs and health; compatibility tests protect existing provider interfaces.
- **Risks:** schemas drifting from runtime behavior, health checks becoming
  credential probes and abstraction pressure from provider-specific features.
- **Dependencies:** plugin registry v1, provider registry, configuration/secret
  loaders, health API, generated clients and operator documentation.

### 7. Establish an operationally repeatable release gate

- **Priority:** must-have.
- **Problem:** v0.2 live evidence is a successful single-node snapshot: ten
  BuildRuns, no metrics-server/API latency, same-code upgrade, and no production
  backup/restore or OIDC drill.
- **User value:** operators receive measured capacity, actionable alerts and a
  rehearsed recovery/upgrade path instead of feature-only confidence.
- **Proposed solution:** publish dashboards and alert thresholds for reconcile,
  queue, runner, webhook, provider and API signals; automate PostgreSQL and CR
  backup/restore drills; run published cross-version upgrade/rollback; record 100
  BuildRun and bounded large-log results with machine-readable budgets.
- **Acceptance criteria:** dashboards and alerts are tested from injected failures;
  backup/restore meets documented RPO/RTO in a disposable environment; upgrade
  retains tenants, CRs, audit and evidence; 100 BuildRuns meet declared terminal,
  p95 latency and resource budgets; a 100 MB log cannot exhaust API/controller
  memory; final gate artifacts are attached to the release review.
- **Risks:** noisy shared-runner metrics, misleading synthetic recovery results,
  storage cost and environment-specific performance.
- **Dependencies:** metrics-server/Prometheus, PostgreSQL, external log/artifact
  stores, release automation, stable tenancy and runner-pool status.

## Milestones and sequencing

1. **Gate debt closure:** outcome 1 must pass before new distributed execution is
   accepted.
2. **Tenant-to-runner slice:** outcomes 2 and 3 land together with denial,
   deprovisioning and failure tests.
3. **Digest-to-lineage slice:** outcomes 4 and 5 prove one production-shaped
   promotion and rollback path.
4. **Operator closure:** outcome 7 is mandatory; outcome 6 is limited to plugins
   required by the supported topology.

Work may proceed in parallel inside a milestone, but the release does not absorb
additional providers or protocols when a prior exit condition is incomplete.

## v0.3 release gates

- No skip in signed-source, authenticated-registry, GitOps commit/PR, Argo CD
  health, OIDC isolation or v0.2-to-v0.3 upgrade conformance.
- Tenant authorization and runner-pool lease tests include denial, restart,
  cancellation, duplicate delivery and credential-compromise cases.
- One promoted and one rolled-back digest have complete source, policy, approval,
  evidence, Git and deployment lineage.
- Go test/vet, Angular build/browser tests, generated SDK checks, production
  dependency audit, Helm render and all security checks pass.
- Backup/restore and the measured 100-BuildRun gate meet documented budgets.
- Zero unexplained critical/high production finding; moderate findings have an
  owner, applicability statement and target date.

## Deferred beyond v0.3

- public/dynamic plugin execution and marketplace distribution;
- SCIM, billing, entitlements and enterprise access-review automation;
- automatic multi-region runner failover or a general cluster fleet scheduler;
- provider parity beyond the topology selected for the release gate;
- stable `v1` storage and removal of `v1alpha1`; and
- general-purpose DAG/workflow semantics.
